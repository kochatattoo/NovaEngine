## Архитектурные решения

### Почему `UIElementComponent` + `UIButtonComponent` + `UIButtonStateComponent` — три отдельных?

- **`UIElementComponent`** — данные (якоря, размер, фон). POD.
- **`UIButtonComponent`** — поведение (callbacks, цвета). Тоже POD, но с `std::function`.
- **`UIButtonStateComponent`** — runtime state (`Hovered`, `Pressed`). Изменяется каждый кадр.

Разделение позволяет иметь **кнопку с текстом, и некнопочный UI** (просто фон, например панель). Если объединить в один мега-компонент — будет много пустых полей.

### Почему `UIAnchorSystem` обновляет `TransformComponent::Position`?

Чтобы UI рендерился через **тот же `UIRenderSystem`** (только с UI camera), а не через отдельный рендер. UI elements — это просто entities с `TransformComponent + UIElementComponent`. UI camera отличается projection (ortho 0..W, 0..H), но тот же pipeline.

### Почему Y invert в `UIAnchorSystem`?

Screen coordinates: Y вниз (0 = top, H = bottom). OpenGL world: Y вверх (0 = bottom, H = top). UI camera projection (ortho 0..W, 0..H) — Y вверх. Поэтому в `UIAnchorSystem::Update` инвертируем Y:
```cpp
float worldY = windowH - (screenY - ObjectAnchor.y * Size.y) - Size.y;
```

Это позволяет `ScreenAnchor = (0, 0)` означать **top-left** (как в CSS/Unity).

### Почему `UIButtonSystem` использует `InputSystem::Get()`, а не `Input` legacy?

`InputSystem` — рекомендуемый API (события + состояния), `Input` — legacy. `MouseButton::Left` + `GetMouseButton` — современный путь.

## Уроки

1. **Mouse position split**: screen pos (Y down) vs world pos (Y up) — нужна инверсия в `UIAnchorSystem`.
2. **`InputSystem::Get()` vs `Engine::Get().GetInputSystem()`** — `InputSystem` это singleton, `Engine::GetInputSystem()` не существует.
3. **Forward-declaration `class NK::Font;`** — для `std::shared_ptr<NK::Font>` в `UITextComponent.h` не нужен полный include, достаточно forward-declaration в namespace `NK`.
