## Корневая причина

В `LuaBindings::RegisterAll` функции регистрируются в таком порядке:

```cpp
void LuaBindings::RegisterAll(LuaManager& lua) {
    LuaClassBindings::RegisterAll(lua);
    LuaComponentBindings::RegisterAll(lua);
    LuaCameraBindings::RegisterAll(lua);
    LuaFuncBindings::RegisterAll(lua);     // 1. Регистрирует GetMousePosition через Window
    LuaInputBindings::RegisterAll(lua);   // 2. ПЕРЕЗАПИСЫВАЕТ GetMousePosition через Input
}
```

В sol2 последняя регистрация **перезаписывает** предыдущую. Поэтому активна регистрация из `LuaInputBindings`:

```cpp
// LuaInputBindings.cpp
lua.RegisterFunction("GetMousePosition", []() -> std::tuple<int, int> {
    int x, y;
    Input::GetMousePosition(x, y);   // ← ЭКРАННЫЕ координаты (GetCursorPos)
    return { x, y };
});
```

А `Input::GetMousePosition` использует `GetCursorPos` — это даёт **экранные** координаты (от верхнего левого угла монитора).

В `game_match3.lua::OnUpdate`:
```lua
local mx, my = GetMousePosition()                                          -- ЭКРАННЫЕ!
local ww, wh = GetWindowWidth(), GetWindowHeight()
local worldPos = gameCamera:ScreenToWorldPoint(mx, my, ww, wh)          -- ожидает КЛИЕНТСКИЕ
```

`ScreenToWorldPoint` в `OrthographicCamera.cpp`:
```cpp
glm::vec2 OrthographicCamera::ScreenToWorldPoint(int screenX, int screenY, uint32_t windowWidth, uint32_t windowHeight) const {
    float ndcX = (float)screenX / windowWidth;
    float ndcY = (float)screenY / windowHeight;
    float worldX = m_Left + (m_Right - m_Left) * ndcX;
    float worldY = m_Bottom + (m_Top - m_Bottom) * ndcY;
    return glm::vec2(worldX, worldY);
}
```

Ожидает **клиентские** координаты (от верхнего левого угла клиентской области окна). Если передать экранные — `worldPos` всегда неверный, `row, col` выходит за границы, `IsValidCell` возвращает false, и клик «не работает».

Дополнительно: `IsMouseButtonDown(1)` в Lua работал через `Input::IsMouseButtonDown(int)` → `GetAsyncKeyState(1)` — должен работать, но это legacy API. Новый `GetMouseButton(MouseButton.Left)` через `InputSystem::GetMouseButton` — надёжнее.

## Решение

### 1. `Engine/Source/Lua/LuaInputBindings.cpp` — убрана кривая регистрация

**Было:**
```cpp
lua.RegisterFunction("GetMousePosition", []() -> std::tuple<int, int> {
    int x, y;
    Input::GetMousePosition(x, y);  // ЭКРАННЫЕ
    return { x, y };
});
```

**Стало:** регистрация удалена. Осталась только правильная версия в `LuaFuncBindings.cpp` (через `Window::GetMouseClientPosition`, клиентские координаты). `LuaInputBindings` по-прежнему регистрирует `GetMousePos()` через `InputSystem::GetMousePosition()` — тоже клиентские.

### 2. `SandBox/assets/scripts/game_match3.lua` — переход на новый API

**Было:**
```lua
if IsMouseButtonDown(1) then  -- legacy
    ...
end
local mx, my = GetMousePosition()  -- ЭКРАННЫЕ (баг)
```

**Стало:**
```lua
if GetMouseButton(MouseButton.Left) then  -- новый API
    ...
end
local mx, my = GetMousePos()  -- клиентские, надёжно
```

Плюс:
- Убраны избыточные `Log`-statements (только ключевые).
- Добавлен комментарий "v0.1.3 — fixed input".
- Добавлен `Log("Match3: START BOARD GENERATION")` для отладки.
- Инициализирован `score = 0` (был неявно nil).

## Уроки

1. **sol2 перезаписывает последнюю регистрацию.** Нужно либо:
   - Убрать дубликаты (как сейчас).
   - Или гарантировать уникальность (например, `RegisterAll_ClientApi` отдельно от `RegisterAll_Legacy`).
2. **`GetCursorPos` vs `ScreenToClient` — частая ошибка WinAPI.** `GetCursorPos` даёт экранные, `ScreenToClient` конвертирует в клиентские. Движок должен использовать клиентские везде для координат мыши.
3. **`Input::GetMousePosition` остаётся legacy.** Новый код должен использовать `InputSystem::GetMousePosition()` (через события `WM_MOUSEMOVE`, lParam — клиентские координаты).
4. **Двойной вызов `Scene::OnUpdate`** — в `Engine::Run` и в `Game::OnUpdate` оба вызывают `m_Scene.OnUpdate(dt)`. Это лишнее, но безвредное (OnUpdate идемпотентный). TODO v0.2: убрать один из вызовов.

## Дополнение (вечер 2026-08-12): ещё один баг — плитки были 1 пиксель

После фикса координат пользователь сообщил:

> «Отклик появился, но визуально ничего не меняется и не обновляется»

То есть клик теперь **детектится** (`GetMouseButton(MouseButton.Left)` работает), но визуально плитки не реагируют — ни на нажатие (scale 1.2x), ни на своп (texture change).

### Корневая причина №2

В `game_match3.lua` плитки создаются через `CreateSolidColorTexture(...)` — это **1×1 пиксель** текстура. У `SpriteRenderer` по умолчанию `m_PixelsPerUnit = 100` и `m_CustomSize = (0, 0)`.

В `SpriteRenderer::Render`:
```cpp
float renderW = (m_CustomSize.x > 0.0f) ? m_CustomSize.x : (float)texW / ppu;
// = (0) ? ... : 1 / 100 = 0.01 мировых единиц
```

На экране 1280×720 (камера `(-5, 5) × (-5, 5)`) 0.01 мировых единиц = **1 пиксель**. Плитки были видны как цветные точки, а не как "кубики". Любые изменения (scale, texture swap) невозможно заметить.

**Дополнительный баг:** для игрового мира (`!m_IsUI`) в `SpriteRenderer::Render` **transform::GetScale() игнорируется** — размер определяется только `m_CustomSize / 2`. Поэтому `obj:GetTransform():SetScale(1.2, 1.2)` не давал визуального эффекта на нажатие.

### Решение

**1. `SandBox/assets/scripts/game_match3.lua`** — в `OnTileChanged` callback:
```lua
sr:SetCustomSize(CELL_SIZE / PPU, CELL_SIZE / PPU)  -- 0.64 × 0.64 мировых
sr:SetPixelsPerUnit(PPU)
```

**2. `Engine/Source/Lua/LuaComponentBindings.cpp`** — добавлены биндинги `SetCustomSize` и `SetPixelsPerUnit` (раньше их не было в Lua API).

**3. Документация обновлена** — в `02_Подсистемы/04_Рендерер_и_камеры.md` добавлен раздел "⚠️ v0.1.3 — Transform::SetScale игнорируется в игровом мире".

### Уроки

1. **Размер плитки должен быть вычислен явно** — `SetCustomSize` или `SetPixelsPerUnit`. Без этого `1px текстура / 100 PPU = 0.01 мировых = 1 экранный пиксель`.
2. **Не полагайся на дефолты** — `m_CustomSize = (0, 0)` и `m_PixelsPerUnit = 100` в сумме дают 1px объект, что бесполезно для визуализации.
3. **`transform::GetScale()` не используется в `SpriteRenderer::Render`** для игрового мира. Это **нарушение SRP** — Transform::SetScale ничего не делает. TODO v0.2: либо использовать scale, либо удалить этот метод из публичного API.

### Дополнение #2 (вечер 2026-08-12): linker-ошибка из-за двух overloads

После исправления пользователь собрал проект и получил linker-ошибку:

```
NK::SpriteRenderer::SetCustomSize: функция не принимает 2 аргументов
```

**Корневая причина:** в `SpriteRenderer` определены ДВА overloads в inline-заголовке:

```cpp
void SetCustomSize(const glm::vec2& size) { m_CustomSize = size; }
void SetCustomSize(float x, float y) { m_CustomSize = glm::vec2(x, y); }
```

В моей lambda в `LuaComponentBindings.cpp` я вызывал:
```cpp
sr.SetCustomSize((float)w, (float)h);  // ← двусмысленный вызов
```

C++ overload resolution не смог выбрать между:
- `SetCustomSize(const glm::vec2&)` — с неявной конверсией `glm::vec2(float, float)`
- `SetCustomSize(float, float)` — exact match

В некоторых компиляторах (MSVC в Release) — это linker-ошибка, потому что inline-функции не экспортируются как символы, и компилятор не может сгенерировать вызов.

**Решение:** в lambda явно конструировать `glm::vec2`:

```cpp
"SetCustomSize", [](SpriteRenderer& sr, double w, double h) {
    sr.SetCustomSize(glm::vec2(static_cast<float>(w), static_cast<float>(h)));
},
```

Это однозначно вызывает `SetCustomSize(const glm::vec2&)` overload. Теперь C++ однозначно выбирает overload, и inline-функция успешно инлайнится.

**Урок:** при наличии overloads всегда disambiguate вручную (`glm::vec2(...)`, `static_cast<>`, `sol::overload<>`), иначе получишь странные linker-ошибки.
