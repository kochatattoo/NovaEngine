### API

`LuaECSBindings` регистрирует класс `ECSWorld` (без конструктора — World* передаётся через глобальную функцию `GetECSWorld`):

```lua
-- Получить World (глобальная функция, SandBox регистрирует)
local world = GetECSWorld()

-- Создание entities
local e = world:CreateEntity("player")      -- с именем
local e2 = world:CreateEntity()              -- без имени
local e3 = world:GetEntityByName("player")  -- найти по имени
world:RenameEntity(e, "enemy_1")
world:DestroyEntity(e)
world:Clear()

-- Компоненты: Transform
world:AddTransform(e, 0, 0, 0)
world:SetPosition(e, 1.5, 0, 0)
local pos = world:GetPosition(e)             -- {x=..., y=..., z=...}
world:SetScale(e, 2, 2)

-- Компоненты: Sprite
world:AddSprite(e, 1, 0, 0, 1)               -- r, g, b, a
world:SetSpriteColor(e, 0, 1, 0, 1)
local col = world:GetSpriteColor(e)           -- {r=..., g=..., b=..., a=...}

-- Проверка/удаление компонентов
world:HasComponent(e, "Transform")            -- bool
world:HasComponent(e)                         -- true если есть Transform
world:RemoveComponent(e, "Sprite")

-- Валидация
world:IsValid(e)                              -- true если entity ещё жив
```

`Match3Game::SetupLuaBindings` регистрирует глобальную `GetECSWorld()`:

```cpp
m_Lua.RegisterFunction("GetECSWorld", [this]() -> NK::ECS::World* {
    return m_World.get();
});
```

### Архитектурные решения

**Почему `entt::entity` (uint32_t) — аргумент, а не receiver?**

sol2 не умеет делать ООП-методы на POD-типах вроде `entt::entity`. Поэтому все операции — методы `World`:
```lua
-- ❌ не работает (entity — POD, нет методов)
e:SetPosition(1, 0, 0)

-- ✅ работает (метод World)
world:SetPosition(e, 1, 0, 0)
```

Альтернатива — обёртка `EntityProxy`, как `Match3BoardProxy`. Дороже по разработке, даёт только синтаксический сахар. Оставил плоский API.

**Почему `GetColorForType` / `SetColor` принимают 4 отдельных параметра, а не glm::vec4?**

sol2 + glm::vec4 — частая головная боль с overloads. 4 float'а — однозначно работает.

## v0.5.1 — Scene::OnRender без game objects

`Engine/Source/Scene/Scene.cpp::OnRender()`:
- ❌ Удалён цикл по `m_Objects` (game objects больше не рендерятся здесь).
- ✅ Остался цикл по `m_UIObjects` (UI рендерится по-прежнему).

**До:**
```cpp
void Scene::OnRender() {
    // game: m_GameCamera
    for (auto& obj : m_Objects) {
        auto* sr = obj->GetComponent<SpriteRenderer>();
        if (sr) sr->Render(gameViewProj);
    }
    // UI: m_UICamera
    for (auto& obj : m_UIObjects) { /* same as before */ }
}
```

**После:**
```cpp
void Scene::OnRender() {
    // Только UI. Game objects рендерятся через SpriteRenderSystem (см. Game.cpp::OnUpdate).
    for (auto& obj : m_UIObjects) { /* same as before */ }
}
```

**Game objects** теперь рендерятся только через `SpriteRenderSystem`. `Scene::m_GameCamera` всё ещё доступна — Match3Game берёт её для SpriteRenderSystem.

## v0.5.2 — Удалён ScriptComponent

**Удалено:**
- `Engine/Include/Scene/ScriptComponent.h`
- `Engine/Source/Scene/ScriptComponent.cpp`
- Из `Engine.vcxproj`: `<ClInclude>` и `<ClCompile>` для ScriptComponent.
- Из `LuaClassBindings.cpp`: регистрация `AddComponent_Script`.

**Почему удалил:**
- Match3 не использует `ScriptComponent` (Match3Game сам грузит Lua-скрипт через `m_Lua.RunScript`).
- Component был задуман для привязки Lua-скрипта к конкретному GameObject'у — но это дублирует функционал `Match3Game::Start()`.
- `Scene::OnStart` всё ещё дёргает `m_Loaded` для script через `ScriptComponent::OnStart` — но теперь `m_Loaded` статический и не зависит от ScriptComponent.

**Что осталось как legacy:**
- `Scene` + `GameObject` + `Component` + `Transform` (Scene) + `SpriteRenderer` (старый) + `TextRenderer` + `Anchor` + `Button` — **не удалял**, потому что UI (`Button`, `Anchor`, `TextRenderer`) активно их использует. Удаление требует переписать UI на ECS — это отдельный спринт v0.3.
