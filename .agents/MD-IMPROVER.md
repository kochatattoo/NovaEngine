# MD-IMPROVER — аудит и улучшение файлов инструкций для агентов

Процедура проверки, оценки и улучшения файлов инструкций для ИИ-агентов в репозитории,
чтобы агент получал оптимальный контекст проекта.

Файл самодостаточен: всё нужное — рубрики оценки, формат отчёта, шаблоны — находится здесь.
Внешних зависимостей нет.

Процедура нейтральна к инструменту. Всё, что специфично для конкретного агента, собрано
в разделе «Особенности конкретных агентов» в конце — читай оттуда только свой подраздел.

**Эта процедура изменяет файлы.** Правки вносятся только после вывода отчёта о качестве
и получения явного согласия автора.

---

## Фаза 1. Обнаружение

Найди все файлы инструкций в репозитории:

```bash
find . \
  \( -name node_modules -o -name .git -o -name Library -o -name Temp -o -name Build \) -prune -o \
  \( -name 'AGENTS.md' -o -name 'CLAUDE.md' -o -name 'CLAUDE.local.md' \) -print \
  2>/dev/null | head -50
```

Дополнительно проверь каталоги правил и вспомогательных инструкций:

```bash
ls -1 .agents/ .claude/rules/ .cursor/rules/ 2>/dev/null
```

### Типы файлов и их расположение

| Тип | Расположение | Назначение |
|---|---|---|
| Корневой файл проекта | `./AGENTS.md` | Основной контекст проекта, коммитится в git, общий для команды |
| Корневой файл Claude Code | `./CLAUDE.md` или `./.claude/CLAUDE.md` | То же для Claude Code; обычно импортирует `AGENTS.md` |
| Локальные переопределения | `./CLAUDE.local.md` | Личные настройки, в `.gitignore`, не расшариваются |
| Настройки пользователя | `~/.claude/CLAUDE.md` | Значения по умолчанию для всех проектов на машине |
| Файл подпроекта | `./packages/*/AGENTS.md` | Контекст уровня модуля в монорепозитории |
| Файл подкаталога | Любое вложенное расположение | Контекст конкретной фичи или домена |
| Вспомогательные инструкции | `.agents/*.md` | Процедуры и правила, подключаемые по ссылке из корневого файла |
| Тематические правила | `.claude/rules/*.md` | Правила по темам, могут ограничиваться масками путей |

**Как это загружается.** Агенты, поддерживающие `AGENTS.md`, читают ближайший к правимому
файлу вариант, поднимаясь вверх по дереву каталогов. Файлы во вложенных каталогах
подгружаются по мере обращения к файлам в них, а не при старте. Содержимое `.agents/`
автоматически не грузится никем — оно читается только по явной ссылке из корневого файла,
и наличие такой ссылки надо проверять отдельно.

## Фаза 2. Оценка качества

Оцени каждый найденный файл по шести критериям, сумма — 100 баллов. Затем примени штрафы.

### Критерий 1. Команды и процессы — 20 баллов

Есть ли всё, что нужно, чтобы собрать, запустить и проверить проект.

| Баллы | Состояние |
|---|---|
| 18–20 | Команды сборки, тестов, запуска и линта присутствуют, копируются и работают как есть |
| 13–17 | Основные команды есть, часть процессов не покрыта |
| 7–12 | Упомянуты отрывочно или без конкретики |
| 0–6 | Команд нет либо они не работают |

Проверяй фактически: сверь команды с `package.json`, `Makefile`, `*.csproj`, CI-конфигами.
Команда, которой нет в проекте, — не пробел, а дезинформация, и это хуже отсутствия.

### Критерий 2. Ясность архитектуры — 20 баллов

Можно ли по файлу понять, где что лежит и куда класть новое.

| Баллы | Состояние |
|---|---|
| 18–20 | Структура каталогов описана, слои и их зависимости понятны, точки входа названы |
| 13–17 | Структура есть, но связи между частями не объяснены |
| 7–12 | Только перечень папок без смысла |
| 0–6 | Архитектура не описана |

### Критерий 3. Неочевидные особенности — 15 баллов

Зафиксировано ли то, что нельзя вывести из чтения кода.

| Баллы | Состояние |
|---|---|
| 13–15 | Подводные камни, ограничения инструментов, отвергнутые решения и причины отказа |
| 9–12 | Часть особенностей описана, часть обнаруживается только на практике |
| 4–8 | Единичные упоминания |
| 0–3 | Ничего сверх очевидного |

Это самый ценный раздел любого файла инструкций: остальное агент способен вывести сам,
а это — нет.

### Критерий 4. Лаконичность — 15 баллов

| Баллы | Состояние |
|---|---|
| 13–15 | Плотный текст, каждая строка несёт информацию, объём разумный |
| 9–12 | Есть вода, но терпимо |
| 4–8 | Много общих мест и пересказа очевидного |
| 0–3 | Текст в основном состоит из воды |

Пересказ того, что видно из кода, и общие best practices вроде «пишите чистый код» —
это отрицательная ценность: они тратят контекст и размывают реальные правила.

### Критерий 5. Актуальность — 15 баллов

| Баллы | Состояние |
|---|---|
| 13–15 | Полностью соответствует текущему состоянию репозитория |
| 9–12 | Мелкие расхождения |
| 4–8 | Заметная часть описанного устарела |
| 0–3 | Описывает проект, которого больше нет |

Проверяй выборочно: существуют ли названные каталоги, файлы, команды, зависимости.

### Критерий 6. Исполнимость — 15 баллов

| Баллы | Состояние |
|---|---|
| 13–15 | Правила конкретны и проверяемы, из каждого ясно, что делать |
| 9–12 | Большинство конкретны, часть расплывчата |
| 4–8 | Преобладают общие пожелания |
| 0–3 | Невозможно понять, чего от тебя хотят |

Ориентир: «отступ 4 пробела» вместо «форматируй код правильно», «`npm test` перед
коммитом» вместо «тестируй изменения», «обработчики API в `src/api/handlers/`» вместо
«держи файлы в порядке».

### Штрафы

Вычитаются из суммы:

| Штраф | Когда |
|---|---|
| −15 | Прямое противоречие между правилами внутри файла или между файлами разных уровней |
| −10 | Корневой файл, грузящийся в каждую сессию, длиннее ~300 строк |
| −10 | Есть `.agents/` или аналогичный каталог, но ссылок на его файлы в корневом файле нет — содержимое мёртвое |
| −5 | Секреты, ключи, токены, внутренние URL в тексте файла |

### Шкала оценок

- **A (90–100)** — полно, актуально, исполнимо
- **B (70–89)** — хорошее покрытие, мелкие пробелы
- **C (50–69)** — базовая информация, нет ключевых разделов
- **D (30–49)** — скудно или устарело
- **F (0–29)** — отсутствует или сильно устарело

## Фаза 4. Точечные правки

После вывода отчёта запроси у автора подтверждение — правки не вносятся молча.

### Правила внесения правок

1. **Предлагай только точечные добавления** — то, что реально полезно:
    - команды и процессы, обнаруженные при анализе;
    - подводные камни и неочевидные паттерны, найденные в коде;
    - связи между модулями, которые не были очевидны;
    - работающие подходы к тестированию;
    - особенности конфигурации.

2. **Держи минимальный объём** — не добавляй:
    - пересказ того, что очевидно из кода;
    - общие best practices, уже покрытые в другом месте;
    - разовые исправления, которые вряд ли повторятся;
    - многословные объяснения там, где хватит одной строки.

3. **Следи за размером.** Файл, который грузится в контекст каждой сессии, должен
   оставаться коротким — ориентир около 300 строк. Если файл разрастается, выноси
   тематические блоки в отдельные файлы и ссылайся на них, а не наращивай корневой.

4. **Показывай дифф.** Для каждого изменения покажи:
    - какой файл правится;
    - конкретное добавление (диффом или цитатой);
    - краткое объяснение, чем это поможет будущим сессиям.

### Формат диффа

    ### Правка: ./AGENTS.md

    **Зачем:** отсутствовала команда сборки, из-за чего было неясно, как запускать проект.

    ```diff
    + ## Быстрый старт
    +
    + ```bash
    + npm install
    + npm run dev  # dev-сервер на порту 3000
    + ```
    ```

## Фаза 5. Применение

После согласия автора внеси правки, сохраняя существующую структуру документа.
Не переформатируй файл целиком, не переставляй разделы без необходимости.

---

## Шаблон корневого файла

Каркас для нового `AGENTS.md`. Бери только релевантные разделы, пустые выбрасывай.

```markdown
# <Проект> — правила для ИИ-агентов

## Проект
Одна-две строки: что это, для какой платформы, на чём.

## Команды
```bash
<сборка>
<тесты>
<запуск>
<линт>
```

## Структура
Дерево каталогов с однострочным пояснением к каждому: что тут лежит и что сюда класть.

## Что нельзя трогать
Файлы и каталоги, правка которых ломает проект. Для каждого — почему.

## Кодстайл
Именование, форматирование, обязательные архитектурные правила. Конкретно и проверяемо.

## Подводные камни
То, что нельзя вывести из чтения кода. Самый ценный раздел.

## Git
Ветки, формат коммитов, что не коммитить.

## Стоп-сигналы
Условия, при которых работа останавливается и задаётся вопрос человеку.

### Дополнения по типам проектов

**Unity.** В «Что нельзя трогать» обязательно: `*.meta`, `*.unity`, `*.prefab`, `*.asset`,
`*.controller`, `*.anim`, `Library/`, `Temp/`, `*.csproj`, `*.sln`. Отдельно — правило про
сериализуемые поля и `[FormerlySerializedAs]`, и про то, что merge-конфликты в YAML-ассетах
разрешает человек.

**Монорепозиторий.** Корневой файл — общее; в каждый пакет свой `AGENTS.md` с локальным.
В корневом — карта пакетов и их зависимостей.

**Библиотека или SDK.** Отдельно: что является публичным API, правила обратной совместимости,
где живут changelog и версионирование.

## Типовые проблемы, которые стоит отмечать

1. **Устаревшие команды** — команды сборки, которые больше не работают.
2. **Пропущенные зависимости** — необходимые инструменты не упомянуты.
3. **Устаревшая архитектура** — описанная структура файлов уже изменилась.
4. **Нет описания окружения** — не указаны нужные переменные среды или конфигурация.
5. **Сломанные тестовые команды** — тестовые скрипты изменились.
6. **Незадокументированные подводные камни** — неочевидные паттерны не зафиксированы.
7. **Противоречия между уровнями** — корневой файл и файл подкаталога требуют разного.
8. **Разросшийся корневой файл** — сотни строк, которые грузятся в каждую сессию.
9. **Мёртвые ссылки** — файл ссылается на инструкции, которых нет, или наоборот:
   вспомогательные файлы есть, но на них никто не ссылается.

---

## Что отличает хороший файл инструкций

**Принципы:**

- лаконичный и читаемый человеком;
- команды исполнимые, копируются и запускаются как есть;
- специфика проекта, а не общие советы;
- неочевидные особенности и предупреждения.

## Особенности конкретных агентов

Читай только свой подраздел.

### Codex

- Читает `AGENTS.md`, включая вложенные — берётся ближайший к правимому файлу.
- Файлы в `.agents/` автоматически не читаются: нужна явная ссылка из корневого `AGENTS.md`.
  При аудите проверь, что такая ссылка есть и путь в ней верный.
- В автоматическом режиме запрос подтверждения из Фазы 4 может не сработать. Если получить
  подтверждение невозможно — останови работу на отчёте и не вноси правки.

### MiniMax

- Ориентируется на `AGENTS.md`.
- Применимо всё то же, что и для Codex, включая замечание про автоматический режим.

### Claude Code

- Читает `CLAUDE.md`, а не `AGENTS.md`. Корректная схема при наличии `AGENTS.md` —
  `CLAUDE.md` с импортом `@AGENTS.md` в первой строке либо симлинк
  (`ln -s AGENTS.md CLAUDE.md`). На Windows симлинк требует прав администратора или режима
  разработчика, поэтому там используется импорт.
- Импорт `@путь/к/файлу.md` подставляет **весь файл в контекст при старте**. Разбиение на
  импорты улучшает организацию, но не экономит контекст. Глубина вложенности — до четырёх
  уровней. Чтобы упомянуть путь без импорта, оберни его в обратные кавычки.
- `.claude/rules/*.md` — тематические правила. Файл без поля `paths` во фронтматтере грузится
  всегда; файл с `paths` подгружается только при обращении к файлам, подходящим под маску.
  Это основной способ не раздувать корневой файл.
- `/context` показывает, какие файлы памяти реально загрузились в текущей сессии; `/memory`
  открывает их на редактирование. Если файл не виден в `/context` — агент его не читает,
  и причину надо искать там. Расхождение между списком на диске и списком в `/context` —
  само по себе находка для отчёта.
- Блочные HTML-комментарии (`<!-- ... -->`) вырезаются перед подстановкой в контекст —
  ими можно оставлять заметки для людей, не тратя токены.
