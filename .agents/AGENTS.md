# Alone In The War

Этот файл — единый источник правды для всех агентов при работе с этим репозиторием

---

## Обзор проекта

- **Название:** Alone In The War (далее `AITW`)
- **Жанр:** Stealth Action RPG от третьего лица с ближним боем, с элементами Immersive Sim в реалистичном средневековом сеттинге
- **Платформа:** Steam (Windows)
- **Стэк:** `Unity 6.3` (6000.3.5f2), `HDRP`, `Input System`, `Zenject`, `Wwise`, `DOTween`,
`Unity Localization`, `UniTask`, `UniRx`, `Addressables`, `Odin`, `Cinemachine`, `UnityHFSM`,
`xNode` (граф квестов), `NuGetForUnity`, `Test Framework`

  Установлено, но нигде не используется (0 обращений в `Assets/Scripts`):
  `com.unity.behavior`, `com.unity.jobs`, `com.unity.visualscripting`, `com.unity.timeline`,
  NuGet-пакет `MediatR`. DOTS/ECS в проекте нет. Наличие пакета — не разрешение
  строить на нём решение; `MediatR` в частности не является нашим механизмом событий.

## Команды

Сборка из CLI не настроена — билд собирается из редактора, дальше PowerShell-скрипты:

```powershell
CI/Package-LocalBuild.ps1     # упаковка локального билда
CI/Archive-Build.ps1          # архивация
CI/Upload-ToYandexDisk.ps1    # выкладка
```

Тесты — только через `unity-mcp` (`run_tests` / `get_test_job`), см. Правило 4.

## Правила

1. Сначала код и текст; остальные файлы — только мелкими правками с отчётом

Файлы кода (в основном `.cs`) и текстовые файлы (в основном `.md`) — основное, с чем ты работаешь

Сериализованные ассеты Unity (сцены, префабы, `.asset`, `.meta` и т.д.) — без спроса допускаются только мелкие правки
(прописать ссылку, починить сломанную/повисшую ссылку, исправить число, задать одно поле или элемент массива).
Отчитывайся о каждой такой правке явно — называй файл и что изменилось, каждый раз, без исключений

Всё крупнее (создание/удаление ассета, перестройка иерархии сцены или префаба, массовые правки по многим ассетам
или любое изменение, эффект которого не очевиден из одной строки описания) требуют явного разрешения разработчика заранее.

2. Никаких коммитов

Никогда не коммить. Коммитит только разработчик.

3. Только русский с исключениями

В ответах и рассуждениях (далее ОиР) используй русский (в планировании тоже). Также комментарии (`summary`) делай на русском

4. Unity MCP: читать и тестировать свободно, изменять — только с разрешения

Сервер `unity-mcp` даёт доступ к запущенному. Используй его не спрашивая для всего, что только читает
(осмотр состояния редактора/проекта, чтение консоли, рефлексия по типам, запросы к сценам/ассетам),
для запуска тестов (`run_tests`/`get_test_job`, `EditMode` и `PlayMode`)
— прогнать набор тестов и доложить реальные результаты ожидается, а не согласовывается —
и для `refresh_unity` (импорт ассетов и перекомпиляция скриптов): после своих правок кода
обнови проект и проверь консоль сам, разрешения на это не спрашивай.

Всё, что изменяет контент или состояние редактора, требует явного разрешения разработчика заранее:
создание/правка/удаление ассетов, скриптов, сцен, префабов, компонентов, материалов, пакетов, сборок,
вход/выход из Play mode, выполнение пунктов меню или запуск произвольного кода в редакторе.

Допущение Правила 1 про «мелкую правку с отчётом» касается того, что можно менять,
а не как — работа через MCP его не ослабляет, и каждое такое изменение по-прежнему требует отчёта.

Никогда не заявляй результат, которого MCP-сервер на самом деле не вернул — сообщай то,
что вернул инструмент, включая ошибки. Если MCP недоступен (сервер лежит, редактор не запущен) — сообщи разработчику об этом
(по возможности пропусти этап) и не приписывай к каждому сообщению дежурную оговорку об этом

5. Тесты должны иметь 2 атрибута и `Metadata`

Ни один тест не пишется без `[Author]` и `[Category]`, описанных в разделе «Тестирование»,
и ни одна папка Tests/ не существует без собственного Metadata.cs. Это требование на момент генерации,
а не задача на последующую уборку — тест без любого из двух атрибутов считается
незавершённой работой, ровно как тест, который не компилируется.

Отдельные тестовые сборки (`*.Tests.asmdef`) не создавай молча — предложи разработчику

6. Стиль ответов: сжатая скоропись

ОиР для разработчика — плотным телеграфным стилем, а не развёрнутой прозой:

Опускай местоимения, артикли, связующий мусор; формулируй максимально плотно — разворачивай объяснение только по запросу.
Никакой вежливости, извинений и слов-заполнителей («вот ответ», «я думаю», «попробую», «конечно», «подожди»).
Используй сокращения («т.е.», «т.к.», «и т.д.», «и т.п.») вместо полных формулировок.

7. Ёмкие `summary`

Не пиши длинные `summary`, не более 3 строчек, желательно 1-2 строки. Если нужно написать длинное объяснение - делай
это отдельным блоком, с отступом в 1 строку от всех элементов, Резервируй такие блоки для фундаментальных вещей
(неочевидный инвариант, отвергнутая альтернатива и т.д.). Не пересказывай то, что код уже говорит сам

8. Создавай `CLAUDE.md` и `AGENTS.md` одновременно

Основной файл для ИИ конфига - `AGENTS.md`, но для поддержки Claude Code, рядом с каждым создавай `CLAUDE.md` со следующим содержанием

```md
@AGENTS.md
```

## Code Style

1. Стили

| Сущность | Стиль | Пример |
|---|---|---|
| Классы, методы, свойства, enum и его значения, публичные поля, константы | `PascalCase` | `HealthService`, `MaxTargetCount` |
| Интерфейсы | `I` + `PascalCase` | `IHealthService` |
| Приватные и static-поля (в т.ч. `readonly`, `[SerializeField]`) | `_camelCase` | `_currentTarget` |
| Локальные переменные, параметры, `out`-параметры | `camelCase` | `targetPosition` |
| Generic-параметры | `T`, `TKey`, `TValue`, `TResult`, `TContext` | |

2. Общие принципы

- Максимальная длина строки - 120 символов.
- Имя отражает назначение; сокращения — только общепринятые: `Id`, `UI`, `VFX`, `SFX`, `HP`, `XP`, `IK`, `GO`, `FSM`, `GOAP`, `RP`. Кустарные (`_mvSpd`, `_tgtSvc`) запрещены.
- Имя не дублирует контекст класса: в `HealthService` метод — `Update()`, не `UpdateHealthService()`.
- Без безликих имён: `temp`, `data`, `obj`, `value`, `item2`.
- Async-методы — суффикс `Async` (в т.ч. UniTask): `LoadSceneAsync`.
- Bool — форма утверждения: `Is`/`Has`/`Can`/`Should`/`Was`. Поля: `_isDead`, свойства/методы: `IsDead`, `CanMove()`. Не `_deadFlag`, `CheckMove`.
- Свойства называются как состояние, не как действие: `Health`, не `GetHealth`.
- Коллекции — во множественном числе: `_targets`, `_activeEffects`. Структуру указываем, если это важно: `_unitsById`, `_effectsByType`. Тип в имени не пишем: не `_targetList`.
- ReactiveProperty: приватное поле — по смыслу (`_health`), публичное readonly-представление — суффикс `RP` (`HealthRP`).
- Комментарии, логи, документация — на русском.

3. Суффиксы классов

| Суффикс | Назначение | Пример |
|---|---|---|
| `Service` | поведение системы, координация | `MovementService` |
| `Model` | runtime-состояние, без зависимости от Unity | `HealthModel` |
| `Settings` | настройки системы (SO) | `CombatSettings` |
| `Config` | конфигурация конкретной сущности (SO) | `EnemyConfig` |
| `Preset` | готовый набор параметров | `EnemyPreset` |
| `Factory` | создание объектов | `EffectFactory` |
| `Provider` | предоставление данных/сервиса | `InputProvider` |
| `Resolver` | выбор подходящей реализации | `SurfaceResolver` |
| `Installer` | Zenject-установщик | `CombatInstaller` |
| `View` | визуальный компонент (MonoBehaviour) | `HealthBarView` |
| `Presenter` | логика управления View | `InventoryPresenter` |
| `Database` / `Catalog` | коллекции данных | `ItemDatabase` |
| `Selector` | выбор объекта | `TargetSelector` |
| `Handler` | обработка события | `DamageHandler` |
| `Processor` | обработка данных | `EffectProcessor` |

- Read-only интерфейсы — префикс `IReadOnly`: `IReadOnlyHealthModel`.
- Абстрактные классы — префикс `Base`: `BaseEffect`.
- MonoBehaviour-компоненты именуются по роли, без суффикса `Component`: `EnemySpawnPoint`.

## Тестирование

Прогон — только через `unity-mcp` (`run_tests` / `get_test_job`), см. Правило 4.
Тестовых сборок две: `Game.Utils.Tests` (`Assets/Scripts/Shared/Tests`) и `Game.Runtime.Tests`
(`Assets/Scripts/Domain/Character/Core/Target/Tests`). Обе `includePlatforms: Editor`,
т.е. фактически весь набор — `EditMode`.

Каждый тест несёт два атрибута, значения берутся из `Metadata.cs` своей папки Tests/:

```csharp
[Test]
[Author(Metadata.Author.Kostya)]    // Oleg = Infer_exe, Kostya = vertoker, Vlad = kochenkov_vladislav
[Category(Metadata.Category.Self)]  // имя .asmdef без суффикса ".Tests", напр. "Game.Utils"
```

`Metadata` — `internal static` класс с вложенными `Author` и `Category`. Новая папка Tests/
заводит собственный `Metadata.cs` со своим `Category.Self`; NUnit-атрибуты берутся
из `NUnit.Framework`, ассерты — там же, асинхронные тесты — через `UnityTest`/UniTask.

## Общее

- Не запускай форматтер по всему репозиторию. Только по файлам, которые правишь.
- Не делай массовых автозамен по всему `Assets/`.
- Не добавляй зависимости и NuGet-пакеты по своей инициативе.

## Архитектура

- **Никаких `FindObjectOfType`, `GameObject.Find`, `SendMessage`** в рантайме.
  Зависимости передаются явно: через `[SerializeField]`, конструктор или Zenject-инъекцию.
- **Никаких новых синглтонов.** Нужен глобальный доступ — регистрируй сервис в подходящем
  инсталлере (`Assets/Scripts/Infrastructure/DI/`) и получай его через `[Inject]`.
  Новый сервис — новая регистрация в существующем инсталлере, а не новый статический класс.
- **Ничего тяжёлого в `Update()`.** Никаких аллокаций, LINQ, `GetComponent`,
  боксинга в кадровых методах. Кэшируй компоненты в `Awake`.
- **`GetComponent` — только в `Awake`/`Start`**, результат в поле.
- **Логика отделена от представления.** Боевые расчёты, инвентарь, квесты
  не должны знать про `UnityEngine.UI` и не должны сами лезть в сцену.
  UI построен по MVP (`Presentation/UI/**/MVP/{Models,Views,Presenters}`) — следуй этому разделению.
- **Данные — в ScriptableObject** (`Infrastructure/Configs`), не в захардкоженных константах в коде.
  Числа баланса правит геймдизайнер, а не программист; часть конфигов приезжает из Google Sheets.
- **Строковые литералы для тегов, слоёв, анимационных параметров, сцен и действий ввода**
  выносятся в существующие статические классы констант:
  `Shared/Constants` (`AnimatorNames`, `InputActionNames`, `SONames` — пути
  `CreateAssetMenu`, `AnimationPriorities`, `Epsilons`, `EditorNames`) и
  `Shared/Scenes` (`SceneName`, `SceneCatalog`). Новый литерал — туда же, а не в код.
- **Событийная модель:** используем существующий `Infrastructure/EventBus` (сигналы —
  `EventBus/Signals`), Zenject-сигналы или UniRx там, где он уже применён.
  Не изобретай второй механизм событий.
- **Состояния и ИИ:** для конечных автоматов — UnityHFSM (`Domain/Character/FSM`),
  для планирования поведения — существующий GOAP (`Domain/Character/GOAP`).
  Не заводи третий подход без обсуждения.
- **Асинхронность:** UniTask предпочтительнее корутин в новом коде, кроме случаев,
  где корутина явно проще. Всегда пробрасывай `CancellationToken`.
- **Загрузка контента** — через Addressables (`Infrastructure/Addressable`),
  не `Resources.Load` в рантайме.
- **Звук** — только через `Infrastructure/AudioSystem` (сервисы, резолверы, параметры),
  не через прямые вызовы `AkSoundEngine`/`AkUnitySoundEngine` из геймплейного кода.
- **VFX** — через `Infrastructure/VFXSystem` (фабрика, резолверы, качество),
  не инстанцированием эффектов вручную.
- Публичные API документируем XML-комментарием, если назначение неочевидно.
- Комментарии — на русском, по делу. Не пиши комментарий, пересказывающий код.
